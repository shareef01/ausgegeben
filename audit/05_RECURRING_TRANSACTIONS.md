## Schedule and write guarantees

Web `web/src/services/recurrence.ts:22` and Android `app/src/main/java/com/aus/ausgegeben/data/entity/RecurringTemplate.kt:34` calculate schedules from the original anchor. Daily and weekly intervals advance civil dates. Monthly and yearly intervals clamp the day in shorter months and return to the anchor day when it exists. The end date is inclusive. A January 31 monthly schedule yields February 29 and March 31 in 2024. A leap-day annual schedule yields February 28 in common years and February 29 in the next leap year. Templates retain their own immutable time zone. The occurrence timestamp is local day start, including midnight gaps and skipped calendar dates. A skipped date and the next valid date can map to the same instant while retaining distinct date keys. Supported civil dates and UTC instants are bounded.

Each generation transaction re-reads the template, category, deterministic expense ID and occurrence receipt. Expense creation, receipt creation and cursor advancement commit atomically. A valid receipt suppresses recreation even after the user edits or deletes the generated record. A mismatched receipt or mismatched existing expense identity raises an issue and quarantines that template. On an ambiguous permission-denied race, the fallback checks both a server-confirmed cursor advance and canonical receipt identity before accepting completion. See `web/src/services/recurringRepository.ts:192`, `:242`, `:256` and `app/src/main/java/com/aus/ausgegeben/data/RecurringRepository.kt:104`.

For concurrent normal generation and supported retry within a ledger generation, there is one canonical expense document path per template/date. The source-level guarantee is idempotent materialization conditional on the trusted template and receipt state. Realization depends on a successful online pass. Deleting a template retains receipts and generated history. A replace restore can intentionally restore an earlier ledger state. Recheck idempotency against the restored receipt set and checkpoint after replacement. An authenticated owner can perform additional raw writes within the rules, so the application transaction contract does not establish a server-side exactly-once scheduler.

Edits and resume deliberately drop older unmaterialized dates by moving the cursor to the first date after the edit day. Pause-only preserves its cursor. Deletion leaves past records alone. These are documented choices in `docs/recurring-transactions.md:9` and are enforced in the repository path at `web/src/services/recurringRepository.ts:168` and `app/src/main/java/com/aus/ausgegeben/data/RecurringRepository.kt:86`.

## AUS-202 · Foreground reconciliation can leave due occurrences outstanding indefinitely

- **Severity / classification / status** — P2 Medium / design limitation / source-confirmed.
- **Affected code** — `web/src/services/recurringStore.ts:32`, `web/src/services/recurringRepository.ts:275`, `app/src/main/java/com/aus/ausgegeben/MainActivity.kt:137` and `:258`, `app/src/main/java/com/aus/ausgegeben/data/RecurringRepository.kt:141`.
- **Reproduction** — Seed one enabled daily template with 45 due dates and no receipts. Open the verified owner's client online and let the initial pass settle. Keep the client open without visibility, connectivity, resume or explicit sync transitions. A second scenario leaves the app open through the template's local midnight.
- **Expected** — A bounded pass reports outstanding work and arranges another bounded pass while the application remains active. A newly due occurrence becomes visible within the stated foreground scheduling interval.
- **Actual** — The pass processes up to 20 dates across all templates, leaving 25 in the one-pass scenario. Web snapshots intentionally do not trigger writes and the listeners only bind initial/online/visibility events. Android triggers at the identified lifecycle and connectivity events. The next due date can wait indefinitely until a later trigger. When there are no active clients, catch-up is likewise deferred by design.
- **Root cause / impact** — The bounded work loop has no continuation or foreground clock wake-up. Displayed balance and budgets can lag and a user may manually add an expected recurring charge before catch-up.
- **Fix** — Return a due-work signal with the pass result. Schedule cancellable bounded continuations with backoff under the current UID and wake a visible session around the next due date. Preserve the transaction's canonical identity and no-offline-write behavior.
- **Regression** — Use a fake clock and one eligible template with 45 missed dates. Assert 20, 20 and 5 acknowledged writes with no duplicates or account bleed. Freeze a foreground client across local midnight. Inject transient failure, disabled network and account switch between passes.
- **Compatibility** — Existing templates, expense IDs and receipts remain valid. Faster catch-up increases the rate of due writes, so keep throttling and meaningful feedback.

## AUS-203 · Standalone receipt can suppress generation without an expense

- **Severity / classification / status** — P2 Medium / design limitation / receipt admission reproduced, subsequent materialization effect source-confirmed.
- **Affected code** — `firestore.rules:566–576`, `web/src/services/recurringRepository.ts:211–248`, `app/src/main/java/com/aus/ausgegeben/data/RecurringRepository.kt:104–138`.
- **Reproduction** — In a disposable enforced emulator, authenticate as a verified owner and create a valid due template. Before materialization, use the SDK to create the receipt directly. Use the exact document ID `templateId_scheduledDate` and payload with the same template/date and SHA-256 hex of the canonical occurrence key. Do not create an expense or modify the cursor. Then run ordinary reconciliation and read both paths and the cursor from the server.
- **Expected** — A normal generation receipt comes from an atomic creation or reconciliation path. A dedicated authorized restore path can import valid historical receipts for edited or deleted expenses.
- **Actual** — Receipt creation checks owner, verified email, account state, shape, key and timestamp. It never checks whether a matching expense or template exists, whether the template cursor advances in the same write or whether a restore is active. The isolated Firestore probe accepted a canonical receipt and read back both the template and expense as absent. The ordinary materializer's canonical-receipt branch advances the cursor while leaving the expense absent. End-to-end materialization of a forged receipt remains a regression step.
- **Root cause** — The client treats identity as historical proof of generation. The server allows a verified owner to assert that identity independently of generation or restore.
- **Impact** — A compromised or bypassing same-owner client can cause the normal app to skip a scheduled transaction and leave an immutable receipt behind. This crosses the client validation boundary within one ledger. Cross-account access remains owner-gated. Historical receipts outlive intentionally deleted generated rows, so checking for the expense during every materialization would break deliberate deletion.
- **Fix** — Bind normal receipt creation to the current template cursor and matching expense in the same commit, with a distinct rules-checked restore protocol for historical receipts. Derive or verify canonical identity wherever the chosen enforcement layer can do so. If the rules cannot express identity derivation, preserve the client check and evaluate a trusted server writer based on the required threat model.
- **Regression** — Reject the standalone create. Allow normal materialization, supported repair of an existing canonical occurrence, retries after ambiguous commits and restoration of a receipt whose expense was intentionally deleted. Verify cross-owner access stays denied.
- **Compatibility** — Grandfather valid legacy receipts and test mixed-version clients before tightening rule predicates. Requiring an active restore state could break earlier clients that can write receipt-only imports.
