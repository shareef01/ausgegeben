# Ausgegeben Deep Production Audit
Date: 2026-09-06

## Overall Verdict
**PASS WITH WARNINGS**

The Ausgegeben application successfully implements a safe, concurrent, offline-capable architecture for financial data synchronization between Android and Web clients. The data model is sound and properly guarded by Firestore rules. Math parity and export security are maintained across platforms. However, several mitigation strategies rely on client-side logic rather than absolute transactional guarantees, requiring careful maintenance.

---

## 1. Architecture and Infrastructure

**Are Firebase settings (hosting, rewrites, headers) correct?**
Yes. `firebase.json` correctly sets `Cache-Control` for static assets and specifically serves `sw.js` as `no-cache, no-store, must-revalidate` to prevent pinning users to stale builds. Security headers (`Strict-Transport-Security`, `Content-Security-Policy`, `X-Content-Type-Options`, `X-Frame-Options`, `X-XSS-Protection`) are properly configured.

**Is there a clear offline/sync strategy?**
Yes. Both clients utilize Firestore's offline persistence. Writes are committed locally and synchronized automatically. The Web client forces a cache clear upon sign-out (`clearLocalFirestoreCache`) to prevent data leakage between accounts on shared devices.

**Do CI and Build systems enforce security?**
Yes. Android builds verify signed releases against a pinned SHA-256 fingerprint in `.github/release-cert.sha256` during `release.yml`, preventing a malicious or accidental release with the wrong keystore. A read-only smoke test verifies production bundles without risking data integrity.

---

## 2. Data Model and Schema Validation

**Are legacy shapes accurately handled?**
Yes. `firestore.rules` explicitly tolerates `cloudId`, `categoryCloudId`, `receiptImagePath`, and `deleted` fields as legacy artifacts. Furthermore, `updatedAt` is tolerated as either a number or a Timestamp. These rules are enforced, and test coverage (e.g., `emulator/legacyShapes.test.ts`) verifies that inert documents do not block healthy row reassignments.

**Is schema validation watertight?**
Yes. Firestore rules (`firestore.rules`) provide the primary schema validation boundary. `validExpense` and `validCategory` enforce exact field types, preventing unknown schema mutations.

**Are indexes declared and built correctly?**
Yes. The required composite indexes are explicitly declared in `firestore.indexes.json`, crucially including `amount` alongside `dateMillis` and `transactionType` (both with and without `deleted`). This correctly supports server-side aggregations (`sum()`) used for budget calculations.

## 3. Security, Privacy, and Access Control

**Is Firebase App Check correctly handled?**
Yes. As documented, App Check is initialized but intentionally unenforced project-wide to support sideloaded Android APKs (which Play Integrity cannot attest).

**Is Account Deletion secure and thorough?**
Yes. Both platforms require reauthentication before deletion, preventing staleness errors from leaving a half-deleted account. 
- **Web:** Reauthenticates, marks `meta/accountDeletion`, deletes all user collections, deletes the Auth user, and wipes local preference stores.
- **Android:** The `AccountActions.kt` implementation mirrors this exact flow, including the critical addition of clearing local DataStore preferences and the Firestore cache so budget limits and reminders do not leak to the next user on the same device.

**Is CSV Export secure from payload injection?**
Yes. Both clients implement an identical defense against spreadsheet formula injection (CSV injection). In `CsvExport.kt` and `analytics.ts` (`csvEscapeField`), fields starting with `=`, `+`, `-`, `@`, `\t`, or `\r` are neutralized by prepending a single quote (`'`), and quotes are properly escaped.

**Is the Android FileProvider export securely bounded?**
Yes. `file_paths.xml` bounds the exported CSV to `<cache-path name="export" path="exports/" />`. The cache directory is also cleared prior to writing the new export file to prevent indefinite data residency.

---

## 4. Concurrency and Resilience

**How is category deduplication and deletion handled?**
The system implements a read-reassign-delete loop. Because Firestore's Web SDK lacks support for query-based transactional reads, this operation is fundamentally exposed to a TOCTOU race condition where an expense could be assigned to a category exactly as it is being deleted. 

Both clients mitigate this by querying for newly linked expenses a second time immediately before calling `deleteDoc()`, narrowing the race window to network latency instead of eliminating it entirely. While not a strict lock, this is an acceptable pragmatic compromise given SDK constraints.

**Are batch writes resilient?**
Yes. Web's `reassignExpenses` attempts to commit in chunks of 450 documents (below Firestore's 500 cap). If a batch is rejected—typically because one document fails a rules check—the chunk gracefully degrades to sequential, one-by-one updates. This ensures that a single bad "poison pill" document does not block the repair of healthy rows.

---

## 5. Math, Money, and Sync Parity

**Are amounts synchronized safely?**
Yes. Both clients use `Locale.US` internally for formatting and parsing, standardizing the decimal separator to a dot (`.`).
- **Web:** Limits precision via `Math.round(amt * 100) / 100` and `amount.toFixed(2)` during CSV export.
- **Android:** Uses `.format(Locale.US, "%.2f", amount)` during CSV export, guaranteeing byte-for-byte output parity.

**How are budget totals calculated?**
Totals are computed server-side via `getAggregateFromServer` (Web) and `.sumMonthExpenses()` (Android). To bypass legacy soft-deleted rows, both clients perform two aggregate queries (one for all expenses, one for deleted expenses) and subtract the latter. This brilliantly avoids client-side 5000+ document reads while keeping quota usage minimal.

---

## 6. Findings and Recommendations

1. **Category Race Condition (Minor Warning):** The mitigation in `deleteCategory` and `deduplicateCategories` shrinks the race window but does not close it. While a true transaction is impossible via SDK queries, this architecture requires careful monitoring if offline bulk-edits become a feature.
2. **App Check Logs (Informational):** Ensure that the unenforced App Check does not flood Firebase quotas with 403 logs. This is acknowledged as a known condition in the project rules.

No source files were modified during this audit. All verifications were executed via read-only tools and baseline CI checks (all passing).
