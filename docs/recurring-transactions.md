# Recurring transactions: implementation contract

Templates repeat daily, weekly, monthly or yearly at intervals 1–365. They belong to `users/{uid}/recurringTransactions/{uuid}`. The anchor is an ISO local date and a persisted IANA timezone; timezone is fixed after creation. Generated records use the start of the scheduled local day. Midnight gaps use the first valid instant; a skipped date uses the next valid day, matching Java `atStartOfDay`. Frequency arithmetic always starts from the original anchor, so January 31 clamps in February and returns to March 31, and February 29 returns in leap years. Optional end dates are inclusive; local dates use 2000–2099 and their generated instants must remain within the existing 2000-01-01 to 2100-01-01 UTC transaction bounds. A start outside that instant range is rejected, and a terminal occurrence outside it ends the schedule.

Authenticated clients reconcile on startup/resume, network recovery and explicit synchronization. This is client-driven materialization, not an always-on background scheduler. Each pass processes at most 20 occurrences across all templates, with continuation on later synchronization; no history queries or per-template listeners. Unmaterialized dates are caught up in chronological order. Cached template viewing is allowed; edits and generation require server confirmation and never enqueue offline financial writes.

A logical occurrence key is canonical JSON `["recurring-v1", templateUUID, scheduledLocalDate]`. Both platforms use the existing SHA-256 expense identity function on these UTF-8 bytes. An immutable receipt at `recurringOccurrences/{uuid}_{yyyy-mm-dd}` records the generated expense ID. This path encoding is unambiguous because both components have fixed validated formats. A Firestore transaction reads the latest template/receipt/expense and atomically creates the ordinary expense and receipt and advances the cursor. Receipts survive template/expense deletion; replay cannot resurrect an instance the user deleted. A committed write followed by client timeout is replay-safe. No template payload is logged or stored in browser localStorage.

Generated transactions become ordinary editable records. Editing the template never rewrites generated history. Template edits and resume set the next occurrence strictly after the edit/resume local day, deliberately discarding older unmaterialized dates. Paused templates do not materialize. Creating a past-dated template intentionally enables bounded catch-up from its start date. Deleting a template stops future generation but retains generated transactions and receipts.

Categories referenced by active or paused templates cannot be deleted or change type until templates are reassigned or deleted. Transactionally maintained category reference counts enforce the barrier in rules as well as clients. Renaming/style changes are allowed. Account deletion sweeps templates and receipts before categories/expenses and verifies emptiness.

Backup schema integration is deliberately deferred while PR #53 remains unmerged. The standalone representation must include templates and occurrence receipts: older backups preserve current recurring state; new-schema merge upserts represented templates/receipts; replace and rollback restore exact represented state. This branch does not redefine schema v2. Final integration and its tests must happen after rebasing onto the category-budget main.

Creation is separate from normal transaction entry. English/German Settings management shows amount, category, schedule, next due and status. No cron/RRULE, Cloud Functions, Cloud Scheduler, exact background timing, historical template versions or FX conversion are promised. Manual screen-reader/device large-font audits are not claimed.

The Firestore emulator may report permission denied for a losing optimistic write before testing its stale version precondition. Clients accept that race only after an authoritative read proves the immutable receipt exists and the template advanced beyond the attempted date. Other permission failures remain failures.

## Validation and integration boundary

Local validation: Web 275 unit tests, 99 rules tests, 106 repository/emulator tests (including two independent SDK clients with enforced rules), and 8 Chromium browser tests passed. Type checking, CSS validation and production bundle build passed. Android's ordinary suite contains 289 cases: 283 passed and the 6 emulator-only recovery cases skipped as intended without emulator ports. The canonical recovery runner then executed all 6 successfully with zero skips, including recurring replay through the reconstructed production graph. Debug, release and instrumentation APK assembly plus Android lint passed.

Shared `fixtures/recurrence.json` proves calendar dates, canonical operation bytes and SHA-256 document IDs match on Android and Web. Tests also cover both DST changes, future starts, inclusive ends, pause/resume, bounded catch-up, deleted occurrence replay, retained history, account switching, stale listener callbacks, category barriers, independent instance edits and ordinary month aggregates. Isolated backup-section serializers on both platforms retain orphan receipts, reject unknown/missing collections and duplicate identities; they are not yet connected to published backup versions.

Adversarial review found and corrected extreme calendar overflow, malformed timezone handling, category counter evaluation on absent mutation IDs, stale cursor validation during schedule edits, the emulator's concurrent stale-commit permission behavior, and select control labels. Android mutation errors retain the editor draft. Keyboard Escape and focus restoration were tested in Chromium; manual TalkBack/screen-reader, physical-device large-font and real process-death tests were not performed.

PR #53 remains separate and unchanged. This branch is based on pre-#53 main and must not be merged or presented as the final merge-ready PR. After #53 merges: rebase; inspect its actual strict backup v2 format; integrate a distinct recurring-capable schema (likely v3), retaining v1/v2 compatibility; add authoritative template/receipt merge, replace and exact rollback snapshots; rerun the canonical matrix; then open the PR and require all CI and post-merge gates. No release, deployment, tag or version bump is included.
