## Shared contracts and limitations

- Modern keyed creates use `SHA-256(exact UTF-8 key)` encoded as 64 lowercase hex characters on both platforms. Existing deterministic documents are returned without changing financial fields. No-key creation intentionally remains UUID-based.
- A preflight legacy `idempotencyKey` query prevents duplicates of existing random-ID rows. An actively running old binary can still race a modern client because Spark has no trusted server uniqueness primitive; current-current concurrency is structurally closed.
- Category documents without `deletionState` remain active. `deleting` blocks new references, operations are resumable, and a failed operation attempts to reopen the source. Old clients can read the extra field but direct old-client deletes are denied rather than allowed to orphan data.
- Soft-deleted expenses still count as category references because the rows persist and future updates/restoration remain subject to referential rules.
- The account-deletion marker contains only `pendingDeletion` and a technical time. It intentionally survives successful cloud wipe so an Auth-delete failure cannot reseed an apparently fresh account.

## Remaining risks

1. A signed CI release APK still needs the emulator launch gate and a real throwaway-account backend exercise before release; the local throwaway key cannot prove update/install behavior.
2. Old released clients retain the query/random-ID idempotency race against each other and against a modern client during the legacy-query window.
3. A category can remain in `deleting` if the process dies and cleanup cannot run. Retrying deletion resumes it; a normal client edit uses merge and does not silently clear the barrier.
4. Firestore/Auth account deletion cannot be globally atomic without a trusted backend. The minimal marker and fail-closed ordering limit that platform constraint.

App Check remains initialized but unenforced, legacy expense/category fields and number-or-Timestamp `updatedAt` remain accepted, Spark/no-Cloud-Functions constraints remain intact, and the WorkManager/R8 keep configuration was not changed.
